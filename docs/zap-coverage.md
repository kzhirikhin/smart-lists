# Карта покрытия ZAP и порядок расширения

Снимок исходников от 2026-10-18, ревизия
`908e5885b1760769c25e1e66acc3d65f73e8ebb5`. Это результат review (`R`),
а не автоматически поддерживаемый CI-контракт полноты. Инвентарь составлен
без нового скана; затем 2026-10-18 реализовано расширение до пяти активных
целей `manual-v2`. Локальная приёмка ниже; расписание не изменено.

## Что уже проверяется

В [пассивном manifest](../test/zap/manifest.ts) 22 сценария. Для 14 разных
именованных Server Actions требуется наблюдение реального запроса, сопоставленного
с manifest текущей сборки. Это подтверждает прохождение выбранного сценария через
прокси, а не устойчивость Action ко всем атакам. Другие запросы могут попадать
в трафик попутно, но их наличие не является обязательным условием completed.

В [активном профиле](../test/zap/active-policy.ts) пять целей:

| Роль | Вход | Изменяемое поле | Ограничение |
|---|---|---|---|
| Anonymous | GET `/en?zap=baseline` | query | Публичная страница, без проверки авторизованных данных |
| Owner | `createList` | `title` | Создание собственного списка, без вариаций `groupId` |
| Recipient | `addItem` | `itemName` | Обычная запись расшаренного списка, без вариаций `parentItemId` |
| Owner | `renameList` | `title` | Переименование своего списка; listId/spaceId заморожены |
| Recipient | `renameItem` | `itemName` | Переименование обычной записи shared list; itemId/spaceId заморожены |

Используются только native-правила 40012 (reflected XSS) и 40018 (SQL injection),
LOW, один поток, общий hard-budget 600 попыток до upstream. Gate сохраняет
сессию, Origin, идентификаторы и служебные поля. Поэтому этот профиль не проверяет
CSRF, обход авторизации, подмену пространств или ролей.

Ответ Server Action в формате RSC не равен странице, на которой впоследствии
отобразится сохранённое значение. Проверка 40012 и успешная мутация не доказывают
отсутствие сохранённого или DOM XSS. Учебная контрольная мишень подтверждает
работу правила, но не полноту проверки отображения данных Smart Lists.

## Инвентарь Server Actions

Разовый обход TypeScript AST нашёл 35 экспортируемых функций в модулях с
`"use server"`, ещё четыре встроенные серверные функции и два API route-модуля.
Прочитаны текущие формы экспортов и связанные потоки. Это не опись всех
HTTP-эндпоинтов, вариантов RSC-протокола, OAuth-переходов или комбинаций аргументов.
После изменения экспортов, форм inline actions или маршрутов карту надо пересмотреть.

В таблицах «Пассивный сценарий» означает обязательную проверку имени Action в
manifest; «—» означает отсутствие такого требования, а не доказанное отсутствие
запроса. Перечислены бизнес-аргументы; FormData также передаёт контекст `spaceId`
и, где предусмотрено, `socketId`. Их нельзя считать свободными текстовыми входами.

### За пределами этих 35 функций

- В [публичной странице](../src/app/[locale]/page.tsx) две inline-функции:
  вход через Google и вход в guest; в
  [AuthenticatedHome](../src/components/spaces/AuthenticatedHome.tsx) ещё две
  inline-функции выхода. Четыре объявления не означают четыре разных
  бизнес-операции или четыре постоянных URL.
- [Auth route](../src/app/api/auth/[...nextauth]/route.ts) экспортирует GET/POST
  библиотечных handlers. Проверка synthetic session не проверяет весь OAuth.
  [Pusher auth route](../src/app/api/pusher/auth/route.ts) имеет отдельный POST;
  native XSS/SQL профиль не подтверждает безопасность realtime-авторизации.
- Гостевые данные редактируются в localStorage. Сценарий браузера проходит через
  прокси, но изменения гостевого списка не становятся серверными мутациями.
  Для них нужны проверки браузера и отображения локальных данных.
- Отрицательные проверки ролей, IDOR, CSRF и space isolation остаются задачей
  целевых security/integration/E2E-тестов. Их нельзя заменить активным сканом,
  который намеренно замораживает эти параметры.

## Первое расширение: переименования

Реализованы `renameList` от owner с изменением только `title` и
`renameItem` от recipient с изменением только `itemName` обычной записи.
Оба действия уже обязательны в пассивном manifest и используют знакомую
FormData. Это добавляет два пути изменения существующих данных, сохраняя
границы текущего стенда и возможность доказать принятые мутации.

Для `renameList` полный путь: UI → `ListsApi` → серверный адаптер с `spaceId`
и `socketId` → auth/budget/resolveActionSpace → Zod (title 1–50) → Prisma
updateMany с ownerId и spaceId → layout revalidate → after/Pusher с исключением
вкладки-автора. Получатель не получает права переименовать список.

Для `renameItem` путь аналогичен, но Zod допускает itemName 1–200, а Prisma
проверяет `listInSpaceWhere` при чтении и обновлении: редактирование содержимого
доступно участнику списка. Проверка этого пути от recipient должна быть явной;
существующий E2E переименования от owner её не заменяет.

Смежная проверка: сохранить контролируемый текст, перечитать после reload и
убедиться, что он отображается как текст без выполнения HTML/скрипта.
Это отдельное доказательство для выбранных UI-путей, не результат правила 40012
и не гарантия отсутствия всех вариантов stored XSS. Сейчас названия отображаются
через React как текст; приёмка должна закрепить это поведение.

После этой группы: `createGroup`/`renameGroup`, затем пространства после
поддержки их wire-формата. Заметки — отдельной задачей: обе операции используют
`expectedVersion`/`noteVersion`. Повтор исходного запроса после первой мутации
может дать только conflict. Нужен протокол обновления версии или новые фикстуры,
с проверкой реально принятых изменений; отключать optimistic concurrency нельзя.
Заметки — обычный текст, не AI Markdown.

## Условия приёмки расширения

1. Захватить реальные запросы текущей production-сборки для обеих новых целей,
   проверить Action ID по manifest сборки, роль, доступ и session до/после атак.
   Для recipient заранее создать разрешённый shared fixture.
2. Расширить точный allowlist до пяти целей: прежние три плюс два переименования.
   На каждой цели разрешить одно текстовое поле; идентификаторы, Origin, cookie,
   служебные RSC-поля и `socketId` сохранять. Запретить незаявленные role/operation
   пары и подмену цели; общий лимит 600 не увеличивать без измерений.
3. Согласованно обновлять gate, activeRunSchema, native-скан, отчёт/publisher и
   контроллер. В `manual-v2` completed требует весь набор из пяти целей,
   seed success, оба завершённых native-правила с запросами, сохранение и
   отображение переименований. Одного добавления browser-сценария мало.
4. Идентичность профиля и scope включают цели, правила и лимиты activePolicy.
   Контроллер хранит digest политики. Старый журнал без profile читается как
   manual-v1, сохраняет исходную дату и даёт profile-outdated, пока новый
   completed не подтвердит текущий digest. Отчёт прежнего набора не принимается
   за новый. При последующих расширениях сохранять этот контракт.
5. Для каждой новой цели доказать не только seed HTTP 200, но и принятые
   изменённые запросы/RSC success и сохранённое состояние. Проверить отображение
   названий после reload отдельно от native alert. Отсутствие параметра,
   потеря сессии, только validation/conflict-ответы, бюджет или незавершённое
   native-правило не должны давать completed.
6. Сохранить контрольную уязвимую мишень вне приложения, fault-пробы,
   санитайзер и точные safe artifacts. Повторить релевантные тесты и локальный
   A/B-прогон, затем проверить опубликованный main-run и обновление журнала.
   CI passive остаётся advisory; расписание, production и внешние сервисы
   этим расширением не меняются.
