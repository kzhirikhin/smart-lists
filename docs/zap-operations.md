# Расписание и состояние ZAP

Этап 6 внедряется без расширения покрытия этапа 5. Реализация подготовлена;
публикация и живая проверка сигналов ещё не выполнены.

## Когда запускается

- Двухфазный `.github/workflows/zap-manual.yml`: 5-го числа каждого месяца,
  10:17 Asia/Tokyo, cron `17 1 5 * *` в UTC. Target — одноразовая локальная
  production-сборка актуального default branch, не production-сайт.
- Вручную: Actions → ZAP Manual (advisory) → Run workflow → main.
  Ветка/тег доступны для целевой диагностики, но в журнал свежести засчитывается
  только default branch того же репозитория.
- Вне очереди: после значимых изменений auth/прав/sharing/space isolation,
  Server Actions/пользовательского ввода, headers/hosting, Next/Auth.js,
  применимого advisory или исправления уязвимости. Инициатор отмечает область
  проверки в PR. Существующий профиль покрывает только три активных входа;
  для остальных нужна отдельная подходящая проверка.

Автоматических повторных атак после failure нет. Владелец разбирает причину,
исправляет её и запускает main вручную; повтор считается успехом только после
обеих фаз. На каждый deploy active scan не добавляется. Cron может задержаться
или не сработать; это не обещание точного времени и не SLA.
GitHub также может отключать расписания публичного репозитория после 60 дней
неактивности. Ограничения: [официальное описание schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## Что считается свежим

Контроллер `.github/workflows/zap-operations.yml` запускается после завершения
ZAP Manual через workflow_run и ежедневно в 11:43 Asia/Tokyo (`43 2 * * *`).
Дневной запуск дополнительно перечитывает завершённые runs, чтобы восстановить
пропущенное событие. Workflow/job сканера advisory: зелёный conclusion не
считается доказательством завершения.

Нужны одновременно:

1. REST подтверждает workflow ID, собственный repository, default branch,
   event schedule/workflow_dispatch и completed source run.
2. Успешны шаги скана, publisher, upload и technical outcome.
3. Точный artifact этого run/attempt содержит девять разрешённых имён.
   run.json и три фазовых JSON проходят схемы, SHA совпадает, dirty=false,
   A/B completed, очередь 0, не control; сессии/успешные изменения полей и оба
   активных правила подтверждены. Scope фаз различны.
4. Дата успеха берётся из completed_at шага анализа, не из cron/начала job.

До 40 дней включительно — свежо; более 40 дней — stale. Failure/incomplete,
отмена, отсутствие artifact или неверный JSON не обновляют последний успех.
Старое событие не откатывает более новый результат; rerun различается по attempt
и фактическому времени завершения. Healthy означает технически полный свежий
анализ, а не отсутствие находок/High и не безопасность всего приложения.

## Долговременный журнал и сигнал

Контроллер ведёт один bot-authored GitHub Issue `[ZAP] Состояние периодического
скана`, назначенный владельцу личного репозитория. Body хранит строгую JSON-сводку:
последний полный анализ и последняя попытка, дата, SHA, run/attempt, счётчики и
фиксированная причина. Комментарии сохраняют историю изменений.

При failure/no-success/stale Issue открывается, новый сигнал содержит упоминание
владельца и ссылку на запуск. Healthy закрывает Issue с комментарием восстановления.
Повторная ежедневная проверка того же состояния не создаёт одинаковые комментарии;
новый неудачный run, переход в stale или ручное закрытие активной проблемы создают
новый сигнал. Задача контроллера красная при проблеме даже при зелёном advisory scan.
При сбое самого контроллера остаётся красный Actions run и фиксированная error-сводка.

История Issue не имеет настроенного срока удаления, остаётся до ручного удаления
Issue/репозитория. HTML/JSON artifacts по-прежнему 30 дней: журнал их не сохраняет
и не заменяет. После ручного удаления/повреждения журнала bootstrap ограничен
100 последними source runs и 20 проверками artifacts; истёкший artifact не доказывает
успех. Если доказательства недоступны, нужен новый полный скан, не ручная отметка healthy.
Не редактировать скрытый JSON-маркер вручную; несоответствие схемы красит контроллер.

GitHub Issue/упоминание — проверяемый сигнал внутри GitHub. Доставка email/push
зависит от настроек владельца и не выводится из успешного API-запроса. Наблюдатель
тоже работает в GitHub: общий сбой/отключение Actions или обоих расписаний не
обнаруживается независимым сервисом. Контролировать дату «Проверено» в журнале.

## Граница доверия

Сканер сохраняет read-only token. Только отдельный контроллер имеет contents:read,
actions:read, issues:write; без production secrets/OIDC, cache-mode:none.
Контроллер всегда делает checkout default branch, не head_sha из workflow_run;
run payload служит указателем и перепроверяется REST. Кода из artifacts не
исполняет: ограниченный ZIP, девять точных имён, unzip -p фиксированных JSON,
строгие схемы, новые body по закрытым полям; сырой текст ошибок не публикуется.
Зависимости ставятся без hooks. Изменения доверенного controller/default branch
и bot-журнала владельцами репозитория остаются внутри доверенной границы.

## Проверка сигналов

ZAP Operations → Run workflow → probe:

- `none`: настоящий журнал, bootstrap/проверка текущего состояния;
- `failure`: синтетический отказ в отдельном Issue `[ZAP] Проверка эксплуатационных сигналов (тест)`;
- `stale`: тот же тестовый Issue, время вычисления смещено за 40 дней;
- `recovery`: возвращает тестовый Issue к настоящему свежему результату.

Пробы не меняют настоящий журнал или дату успеха. Для них уже должен существовать
проверяемый полный source scan. Приёмка: красные failure/stale runs, видимые
комментарии/упоминание/assignee, закрытие после recovery; затем настоящий
workflow_run после нового source scan. Срабатывание будущего месячного cron и
email не выдавать за проверенные по наличию YAML.

## Находки

Разбор security-находок и точные решения остаются в [zap-triage.md](zap-triage.md).
Этот контроллер сигнализирует о выполнении/давности. Отдельная автоматизация
новых High, увеличение покрытия и независимый внешний watchdog сюда не включены.
