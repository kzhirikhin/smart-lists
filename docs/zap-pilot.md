# Локальный пассивный пилот ZAP

Этап 2 [плана](zap-plan.md), 2026-10-16. CI не изменяется. Это проверка
работоспособности контура и заявленного покрытия. Этап 3 добавил
[очищенные отчёты, решения и сравнение](zap-triage.md); историческая приёмка
пилота ниже описывает этап 2.

## Запуск

Нужны работающий Docker Desktop с Linux containers и Node 24 на хосте.
Из корня репозитория:

```powershell
npm run test:zap:pilot
```

Команда собирает Linux-образ с `npm ci --ignore-scripts`, явно генерирует Prisma
Client, устанавливает Chromium и собирает Next. Dockerfile-specific ignore
исключает `.env`, `.git`, локальные credentials, node_modules и прежние отчёты.
На фазе сборки сеть нужна для пакетов/Chromium/next-font; это не фаза скана.

Затем создаются уникальный Compose project, БД `smartlists_zap_test`, приложение
и ZAP. Все три делят network namespace одноразовой БД: localhost сохраняет
существующий TLS-guard приложения, а Chromium не обходит прокси для loopback.
Сеть Docker `internal`, без публикации портов, host mounts, Docker socket и
внешних credentials. В контейнеры не передаётся окружение хоста; Compose читает
пустой явный env-file. Это изоляция тестового стенда, не универсальный sandbox
для враждебного Docker daemon/ядра или произвольного кода на машине.

Предварительная TCP-проба к внешнему IP должна завершиться отказом/таймаутом.
Она проверяет одну точку, не все IP/протоколы; основной сетевой барьер — internal
network. Все процессы скана используют один namespace. Browser routes дополнительно
отклоняют HTTP вне `http://localhost:3100` и закрывают WebSocket. Это намеренное
исключение Pusher/внешних ресурсов, не их проверка. Приложение и ZAP ограничены
сетью Docker, а не browser routes. Dev/production БД не используются.

Перед readiness применяются миграции к фиксированной тестовой БД, затем обычный
globalSetup проверяет миграции/очищает эту же БД. Очистка не выполняется между
сценариями. При нормальном завершении/ошибке удаляются только ресурсы project
этого запуска; остаток после принудительного завершения процесса/сбоя Docker
нужно проверить вручную. Ошибка штатной cleanup меняет итог на incomplete.
Образы/build cache остаются локально для следующих запусков.

## Что считается покрытием

Точный набор: [manifest](../test/zap/manifest.ts), 22 сценария. 18 переиспользуют
существующие E2E без копирования, четыре проверяют публичный вход ru/vi/en/ja.
Один worker, без повторных попыток. Manifest ручной и не доказывает полноту.

- Штатные assertions E2E должны пройти: DOM, перезагрузка/БД там, где сценарий
  уже их проверяет. HTTP 200 не подменяет эти assertions и не доказывает
  серверный успех всех возможных операций.
- Auto-fixture маркирует каждый BrowserContext техническим ID сценария и номером
  контекста. В пилоте это касается и `browser.newContext()` второго участника.
  Browser-level proxy и отключение loopback bypass проверяются реальной историей ZAP.
- Для каждого сценария необходим HTML-трафик основного контекста; для auth —
  HTML пространства с cookie сессии и успешный E2E. Для sharing/revoke необходим
  трафик второго авторизованного контекста, для sharing — его `addItem`.
- Для мутаций проверяются конкретные имена Actions из `Next-Action` по
  `node`-таблице `.next/server/server-reference-manifest.json` текущей сборки.
  Ключ шифрования не выводится. Служебный `rememberSpace` не заменяет `createList`.
  Multipart без `Next-Action` учитывается как общий POST (гостевой вход), но
  не подтверждает именованную мутацию. При изменении формата manifest — error
  или incomplete, а не молчаливый пропуск.
- Переключение/создание пространств и изоляция группы требуют запросов двух
  разных пространств. ID остаются в памяти; в отчёте только число.
- После закрытия браузеров ожидается нулевая очередь passive scan. Сборщик
  запрашивает только views API; spider/activeScan не вызываются.

Поиск и гостевые CRUD локальны: анализируется связанный HTTP-трафик, а не
localStorage как серверная поверхность. Настоящие Google OAuth, S3, AI и
Pusher, production TLS/cookie/edge, полное исполнение прав и все Actions
не покрыты. Сохранённая слабая CSP остаётся отдельным известным вопросом.

## Результат и бюджеты

`test-results/zap-pilot/<timestamp>-<probe>/pilot.json` исключён из Git.
Это безопасная техническая сводка: статусы сценариев/покрытия, числа запросов
и находок по уровням, очередь, длительность, ZAP/addon versions, digest образов,
HEAD и признак dirty. HEAD с dirty не идентифицирует весь рабочий diff;
image ID указывает локально проверенный образ. Находки не разобраны и их
числа не означают число уникальных уязвимостей.

Сырые заголовки/тела используются только в памяти сборщика; session DB ZAP,
Playwright trace/video/screenshots и raw report не экспортируются. Ошибки тестов
и SDK не сериализуются в сводку. На этапе 3 добавлены report.json/HTML/Markdown
и run.json с извлечением evidence по конечным словарям. Неизвестное редактируется
и не сравнивается автоматически; публичной публикации пока нет.

Коды команды: 0 — completed, 2 — incomplete/error. Это локальная диагностика,
не решение о блокировке CI. Сбой сборки/старта/экспорта даёт безопасный error-report.
Ошибка обязательного сценария, отсутствие трафика или очередь дают incomplete.
Общий бюджет пилота 10 минут, workflow-обвязки 20 минут плюс до минуты cleanup.
На холодной машине загрузка Chromium/образов может потребовать отдельной
подготовки/увеличения бюджета; timeout не выдаёт completed.

## Контрольные пробы

Каждая команда создаёт собственную пустую БД. Ожидаем incomplete и ненулевой код:

```powershell
npm run test:zap:pilot -- --probe=proxy
npm run test:zap:pilot -- --probe=session
npm run test:zap:pilot -- --probe=empty
npm run test:zap:pilot -- --probe=queue
```

`proxy` направляет Chromium на закрытый локальный порт; `session` отбрасывает
тестовую auth-cookie перед добавлением в контекст; `empty` выбирает 0 тестов.
`queue` после реального анализа подставляет pending=1 перед оценкой результата:
это явная fault injection, не создание настоящего зависшего сканера. Проверка
реального зависания конкретного scan rule этой пробой не доказывается.

Обычные E2E продолжают использовать `playwright.config.ts`; fixture меняет
поведение только при `ZAP_PILOT=1`. Полный регрессионный прогон без ZAP выполнен
на отдельном Docker-стенде с эфемерной БД и `ZAP_PILOT=0`: 143 теста прошли.
Внешние сервисы при этом недоступны; их ошибки не отменяли успешные DB-мутации.
