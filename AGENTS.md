# Инструкции для ИИ-агентов

Этот файл действует для всего репозитория. Его цель — хранить короткие обязательные правила работы. Актуальное состояние и устройство проекта описаны в `PROJECT_MEMORY.md`, модель угроз — в `THREAT_MODEL.md`.

## Перед началом работы

1. Прочитай `PROJECT_MEMORY.md`.
2. Проверь `git status` и не перезаписывай несвязанные пользовательские изменения.
3. Сверяй документацию с кодом. При расхождении источниками истины являются `package.json`, `prisma/schema.prisma`, миграции и актуальные исходники.
4. Перед изменением функции изучи весь связанный поток: Server Component, клиентский адаптер, Server Action, валидацию, Prisma-запрос и realtime-уведомление.
5. Перед любым значимым изменением сверься с `THREAT_MODEL.md`: определи,
   какие активы, границы доверия, угрозы, допущения и принятые риски оно может
   затронуть. Значимым считается изменение поведения, архитектуры, модели
   данных, прав, Server Actions, внешних интеграций, вложений, логирования,
   лимитов, зависимостей, security headers или процесса деплоя.

## Архитектурные правила

- Используй Server Components по умолчанию. Добавляй `use client` только для состояния, событий, браузерных API и клиентских библиотек.
- Основные мутации выполняются через Server Actions в `src/app/actions/`. Не создавай API route без реальной необходимости.
- Клиентские компоненты списков работают через `ListsApi`. Сохраняй совместимость серверной и гостевой реализаций для поддерживаемых гостем операций.
- Авторизованные данные хранятся в PostgreSQL через Prisma. Гостевые данные хранятся только в `localStorage` браузера.
- Все списки, группы и размещения расшаренных списков привязаны к пространству. Не теряй `spaceId` на пути от URL и провайдера до Action и Prisma-фильтра.
- Для доступа к спискам используй `listInSpaceWhere`, `canAccessListInSpace` или эквивалентную проверку по БД. Никогда не доверяй присланным клиентом идентификаторам и ролям.
- Разделяй действия владельца и редактора. Операции владения, удаления, переименования и управления доступом сохраняют проверки владельца; изменение содержимого доступно участникам согласно `ListShare`.
- Проверяй авторизацию до защищённых операций через `auth()`.
- Валидируй недоверенные данные Zod-схемами через `.safeParse()`. Клиентская валидация служит только UX.
- После успешной мутации сохраняй существующую схему: layout-level `revalidatePath`, затем realtime-уведомление через `after`, если оно требуется.
- Передавай Pusher `socketId` и исключай вкладку-автора: она уже получает свежий RSC payload из ответа Action.
- Сбой Pusher или фоновой очистки S3 не должен откатывать завершённую мутацию БД; ошибку нужно безопасно залогировать.
- Сохраняй two-phase поток вложений `PENDING -> S3 -> HeadObject -> UPLOADED`. Не переноси AWS SDK или секреты в клиентский код.
- Заметки используют `noteVersion` для optimistic concurrency. Не обходи проверку ожидаемой версии.

## Код и интерфейс

- TypeScript работает в strict-режиме. Не добавляй `any` без документированной причины.
- Используй алиас `@/` для импортов из `src/`.
- Компоненты называй в PascalCase, функции и переменные — в camelCase.
- Комментарии и проектную документацию пиши на русском. Объясняй причины и неочевидные ограничения, а не синтаксис. Исключения — два файла, оба адресованы наружу и оба ведутся на английском: `README.md` как публичное описание проекта и `LICENSE` как юридическое уведомление. Меняя любой из них, сохраняй английский и не смешивай языки внутри файла.
- Пользовательский текст добавляй через `next-intl`. При новом ключе синхронно обновляй `messages/ru.json`, `vi.json`, `en.json` и `ja.json`.
- Сохраняй минималистичный визуальный язык, светлую и тёмную темы, адаптивность и доступность.
- Для оптимистичных изменений придерживайся существующих React-паттернов и сверяй состояние с серверным результатом.
- Не логируй секреты, токены и приватное содержимое. Для идентификаторов используй `hashId`, когда это уместно.

## База данных и миграции

- При изменении модели обновляй `prisma/schema.prisma` и создавай новую миграцию. Не переписывай уже применённые миграции.
- Сохраняй составные ограничения, каскады и индексы, обеспечивающие принадлежность сущностей пространству и пользователю.
- Каскадное удаление строки `Attachment` не удаляет объект из S3; предусматривай отдельную очистку.
- Не выполняй опасные запросы и миграции против неизвестной или production-базы без явного согласования.
- Доступ к control plane Neon и любой другой платформы бери по разделу
  «Доступ к платформам» в `SECRETS.md` — см. правила ниже.

## Доступ к платформам

Neon, Vercel, AWS, GCP, GitHub. Свойства их credentials различаются сильно и
неинтуитивно — у одной платформы нет отзыва, у другой нет сужения, — поэтому
выбирать способ входа по здравому смыслу здесь нельзя.

- **Перед тем как взять доступ, открой раздел «Доступ к платформам» в
  `SECRETS.md`.** Там для каждой платформы сведено: чем логиниться, чем сузить,
  как отозвать, что остаётся на диске и какая ловушка. Действуй по нему, а не
  по общей эрудиции, и не изобретай альтернативный способ входа.
- **Советуя пользователю способ доступа, опирайся на тот же раздел.** Совет
  «залогинься в CLI» без сверки с таблицей — источник постоянного доступа,
  который потом никто не вспомнит отозвать.
- **Доступ берётся под задачу и отзывается после неё.** Если в задаче ты его
  брал, напомни об отзыве **отдельным пунктом финального отчёта**, а не
  вскользь. Забытый доступ ничем себя не выдаёт: всё работает одинаково и с
  ним, и без него, поэтому заметить пропущенный отзыв невозможно.
- **Новая платформа — сначала строка в таблице, потом использование.** Строка
  описывает сужение, срок, отзыв, инвентарь и то, что остаётся на диске. Без
  неё нельзя ни выбрать способ входа, ни оценить, чем грозит утечка.

## Зависимости

- Не запускай `npm install` под Windows. npm вычищает из `package-lock.json` optional-зависимости других платформ — wasm-биндинги `@emnapi/*`, которые тянут `@tailwindcss/oxide` и `@rolldown/binding`. Локально это незаметно, а `npm ci` в CI падает на рассинхроне lock и `package.json` ещё до тестов, за считанные секунды. Симптом в логе: `Missing: @emnapi/core@… from lock file`.
- Меняя зависимости, пересобирай lock в той же среде, что и CI:

  ```bash
  docker run --rm -v "$PWD:/app" -w /app node:24 npm install --package-lock-only --ignore-scripts
  ```

- `npm ci` безопасен на любой платформе: он не переписывает lock.
- Ставь зависимости без install-хуков: `npm ci --ignore-scripts`, а затем
  `npx prisma generate` явно. Хуки `preinstall`/`postinstall` исполняются от
  самого факта установки, без единого импорта, и это главный вектор доставки
  в npm — так работала компрометация axios 1.14.1 в марте 2026. Правило
  действует и в CI, и на рабочей машине: именно там лежат токены к консолям.
  Проверено, что при `--ignore-scripts` собираются и Prisma Client, и Next. Собранный на Linux lock корректно ставится и под Windows.
- Обновления версий приходят от Dependabot с выдержкой в семь дней и
  группами; настройка — в `.github/dependabot.yml`. Автомерж не включаем:
  зелёный CI закладку не ловит. Мажоры делаются руками, по одному, своей
  задачей — они исключены из автоматического потока намеренно.
- Уязвимости транзитивных зависимостей, которые Dependabot не закрывает сам, поднимай через `overrides` в `package.json`. Ключ привязывай к мажору (`"minimatch@3"`, `"minimatch@9"`), иначе потребители старого мажора уедут на новый с несовместимым API.
- Не поднимай через `overrides` то, что закреплено внутри `next` — сейчас это `postcss` и `sharp`. Это версии, на которых Next не тестировался; их закрывает очередной релиз самого Next.
- Перевод строки во всём репозитории — LF, правило закреплено в `.gitattributes`. Если инструмент переписал файл в CRLF, верни LF до коммита: иначе дифф раздувается на весь файл и реальные правки в нём тонут.

## Проверка изменений

**Политика тестирования (обязательна).**

- Весь основной функционал приложения должен быть покрыт тестами: списки,
  записи, порядок, заметки, поиск, группы, пространства, совместный доступ,
  гостевой режим, права доступа и привязка к пространству. Меняя поведение,
  поддерживай тесты в актуальном состоянии — правь существующие и добавляй
  новые под новое или изменённое поведение. Изменение без обновления тестов
  считается незавершённым.
- Перед каждым commit и push прогоняй релевантные уровни тестов и убеждайся,
  что они зелёные. Минимум всегда — статические проверки и юниты; при
  затронутых Server Actions/доступе — интеграционные; при затронутом UI-потоке
  — E2E. Не коммить и не пушь с падающими или неактуальными тестами.
- Непокрытое автотестами поведение (OAuth, Pusher, вложения, AI) проверяй
  вручную и сообщай, что именно проверено.

- Минимальная статическая проверка: `npm run lint` и `npm run typecheck`.
- `npm test` — юнит-тесты Vitest. Прогон не требует БД и секретов, поэтому запускай его всегда.
- `npm run test:security:static` — отдельный быстрый gate статических security-контрактов. Он не заменяет `npm test`; запускай его при изменении security-контролей, CI или его manifest.
- Меняя чистую функцию или Zod-схему в `src/lib`, обнови или дополни соседний `*.test.ts`.
- Меняя Server Action или логику доступа, прогони и дополни интеграционные тесты: `npm run test:integration:db` (поднять Docker-БД), затем `npm run test:integration`. Файлы — `test/integration/*.int.test.ts`.
- Для существенных изменений дополнительно проверь `npm run build`, если доступно безопасное окружение.
- `npm run migrate:deploy` выполняет `prisma migrate deploy`. Не запускай его с неподтверждённым `DIRECT_URL`.
- Меняя пользовательский поток в интерфейсе, прогони E2E: `npm run test:e2e:db` (поднять базу), затем `npm run test:e2e`. Файлы — `test/e2e/*.e2e.ts`.
- Новые элементы, нужные тестам, помечай `data-testid`. Не завязывай селекторы на текст: он переводится на четыре языка.
- В E2E не чисти базу между тестами и не считай строки по всей таблице: тесты идут параллельно под собственными пользователями, фильтруй запросы по своим идентификаторам.
- Для непокрытого поведения (OAuth, Pusher, вложения, AI) выполни целевую
  проверку вручную и сообщи, что проверено. Вложения локально проверить нельзя:
  учётных данных S3 там нет с 2026-09-04, `isS3Configured()` возвращает false и
  загрузка выключена. Их ручная проверка выполняется на Preview — там настоящий
  бакет и та же федерация, что в production. Не заводи ради этого локальный
  ключ: presigned POST ценен тем, что условия проверяет сам S3, поэтому подмена
  хранилища локальной заменой дала бы ложную уверенность.
- Проверь итоговый diff на секреты, артефакты сборки и несвязанные правки.
- Перед каждым commit и push подтверди, что влияние изменений на модель угроз
  повторно проверено, а `THREAT_MODEL.md` либо обновлён в этой же задаче, либо
  осознанно оставлен без изменений, потому что зафиксированные факты,
  допущения, статусы и риски не изменились.

## Модель угроз

`THREAT_MODEL.md` — единая точка, где хранится актуальное состояние
безопасности приложения: DFD, границы доверия, активы, открытые и принятые
риски, реестр допущений и план. Это живой документ, а не разовый отчёт; он
ведётся тем же циклом, что и код.

- **До реализации любого значимого изменения** открой актуальную сводку,
  затронутый фрагмент DFD и связанные строки реестра допущений. Зафиксируй для
  себя результат impact-check: что меняется, какие существующие контроли должны
  сохраниться и появляется ли новая угроза или граница доверия. Если влияния
  нет, это тоже должно быть осознанным выводом, а не пропуском проверки.
- **После реализации** повтори impact-check по фактическому diff и сверь реестр
  допущений: не сломала ли правка строку, которая была истинной. Переоценивать
  весь документ заново не нужно — проверяется только затронутый фрагмент.
- **Обновляй документ в той же задаче**, если появилась новая граница доверия
  или внешний сервис, изменились архитектура, активы, права доступа, состав
  передаваемых наружу данных, лимиты, зависимости безопасности, обработка
  credentials или секретов, статусы угроз, принятые риски, триггеры пересмотра
  либо реестр допущений. Обновление обязательно также при закрытии пункта плана
  или снятии неопределённости. Меняя статус, меняй контроль и обоснование.
- **Перед commit и push** итоговая сводка `THREAT_MODEL.md` должна описывать уже
  реализованное состояние, а не состояние до правки. Закрытый риск нельзя
  оставлять открытым в таблице, а новый gap — прятать только в поясняющем тексте.
- **Новое допущение записывай в реестр сразу** и указывай, чем оно защищено.
  Прочерк допустим и означает известный gap; молчание — нет. Если допущение
  выразимо тестом или правилом линтера, лучше закрепить его так, а не текстом.
- **Каждая строка реестра несёт метку доказательства** — `T`, `T*`, `R`, `M`
  или `—` — и дату проверки; легенда лежит под таблицей. Метка отвечает не на
  вопрос «истинно ли допущение», а на вопрос «что заметит его поломку»: `T`
  проверяется каждым прогоном CI, `M` и `R` устаревают молча. Новая строка без
  метки делает таблицу непрозрачной, поэтому метка ставится сразу, вместе со
  строкой.
- **Метку `T` ставь только после проверки самого теста, а не его имени.**
  Утверждения о полноте («покрыты все действия», «новое красит прогон») ломаются
  чаще прочих и незаметно: список, который ведётся руками, остаётся зелёным для
  всего, что в него не попало. Такой тест закрепляет перечисленное, но не
  полноту — это `R`. Полнота обеспечена, когда набор берётся из источника факта:
  обход каталога, экспортов модуля или схемы, а не из массива в тесте. Так уже
  дважды ломались A51 и A29.
- Полный пересмотр — по триггерам из последнего раздела документа, не по
  календарю.
- Источник истины при расхождении — код обоих репозиториев, а не документ.
  Найденное расхождение правь сразу и правь на стороне документа.
- Утверждения об инфраструктуре вне репозитория (Cloud Run, S3, Neon, дашборд
  Pusher) проверке кодом не поддаются. Помечай их статусом `unknown` и не
  выдавай за контроль, пока проверка не выполнена вручную.

## Обновление проектной памяти

Обновляй `PROJECT_MEMORY.md` в той же задаче, если изменились:

- архитектура, модель данных или права доступа;
- зависимости, команды, переменные окружения или внешние сервисы;
- маршруты, ключевые пользовательские потоки или существенные лимиты;
- важное принятое решение или известное ограничение.

Не записывай туда пошаговую историю работы, временные отладочные детали, предположения и секреты. Обновляй дату снимка и сохраняй файл компактным.
